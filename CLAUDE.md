# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Unity 6 (editor `6000.3.10f1`, URP) social VR application: a paired virtual visit to a 1970s women's political prison in Francoist Spain. Visitors appear as live volumetric video via the **VR2Gather** package (`nl.cwi.dis.vr2gather` 1.4.3, from CWI). Users move through "cells"/spaces, hear ex-inmates (volumetric video), and pick up or touch objects (Gaussian splats or AI-generated models) that trigger sounds and voiceovers. Targets: desktop (Win/Mac/Linux, screen or tethered HMD) and native Meta Quest (Android).

## Building and running

There is no CLI build, lint or test setup. Everything is done in the Unity Editor.

- Desktop: open the project, open the `VRTLogin` scene (VR2Gather login manager), press Play. Requires the *cwipc* point-cloud package installed on the machine.
- Quest: install Android build support, select Android and the target HMD in Player Settings, then Build. *cwipc* is not needed there (native Android support is bundled).
- `git lfs install` is required before cloning. `.gitattributes` stores `.asset`, `.ply`, `.tga`, `.bin`, `.bytes`, native libraries and similar as LFS.
- Claude can't run the Editor. Script edits get recompiled when the user refocuses Unity, so ask them to paste any compile errors back.

## Architecture

- **VR2Gather does most of the work.** Networking, sessions, orchestrator connection, user representation (point cloud / avatar), audio and transport all come from the git-sourced packages in `Packages/manifest.json` (`nl.cwi.dis.vr2gather*`, `nl.cwi.dis.cwipc`). Project scripts only add experience-specific behaviour on top of its `VRT.Pilots.Common` namespace.
- **Project scripts** are few and live in `Assets/Scripts/`. The key pattern: `NetworkCollider` extends VR2Gather's `NetworkTrigger` and calls `Trigger()` on `OnTriggerEnter`. Subclasses override `Trigger()`. For example, `TriggerSceneSwitch` waits 30s, then activates a `sceneSwitch` GameObject. Networked interactions should go through `NetworkTrigger`/`NetworkCollider` so both visitors see them.
- **Scenes** are the spaces of the visit: `ReceptionCell`, `CommonCell`, `InterviewCell`, `Corridor`, `Yard`, `Pilot0` (in `Assets/`). Scenes are enabled in `ProjectSettings/EditorBuildSettings.asset`. That list still includes the older `Samples/VR2Gather/1.2.16/...SoloPlayground` alongside the `1.4.3` samples, and `Assets/Samples/VR2Gather/1.4.3/VRT Essential Assets/` holds the login manager, Pilot0 and playground scenes imported from the package.
- **Content assets:** `Assets/Pointclouds`, `Videos`, `Sounds`, `Models`, `Prefabs`, `Photographs`. Object visuals use Gaussian splatting (`GaussianSplatting*.csproj`) and glTF (`org.khronos.unitygltf`). XR input uses XR Interaction Toolkit 3.3.1 with hands, OpenXR and the Oculus package.

## Runtime configuration (repo root)

- `config.json` is the VR2Gather global config. It is regenerated by VR2Gather (see the "Regenerated config.json" commit) and holds the orchestrator URL, transport (DASH/WebRTC) settings, auto-start options and so on.
- `config-user.json` holds per-user settings (user name, representation type: `SimpleAvatar` vs point cloud, camera and mic). `cameraconfig.json` is the camera setup for volumetric capture.
- These are tracked in git, so check `git diff` before committing, since the editor and VR2Gather rewrite them.

## Gotchas

- Don't edit generated or ignored paths: `Library/`, `obj/`, `Logs/`, `UserSettings/` and the root `*.csproj` / `.sln` files.
- `.unity`, `.prefab` and `.asset` files are Unity YAML. Hand-editing is risky (GUIDs, fileIDs). Prefer having the user make scene or prefab changes in the Editor, and keep `.meta` files with their assets.
- `Assets/_Recovery` holds Unity's auto-saved scene recoveries, not source.
- Package upgrades have been painful (see recent commits, "Updated to Unity 6 and VR2Gather 1.4.3"). Git-URL packages in `manifest.json` aren't version-pinned, except SocketIOUnity, so upstream changes can break the build.

## Working conventions

- **Two visitors, always.** Every interaction must work for both and stay in sync. Use VR2Gather's networking (`NetworkTrigger` and related classes) and don't write custom sync.
- **Subclass before overriding.** Package code is read-only (`Library/PackageCache`). Put project versions in `Assets/Scripts`, subclassing VR2Gather classes where possible. Only embed a package in `Packages/` or fork it if a class can't be extended, and tell the user first.
- **Spaces are designed in the Unity Editor by the user.** Claude writes scripts and says which components and Inspector fields to set up. It doesn't hand-edit scene or prefab YAML.
- **Upstream bugs.** If a bug seems to come from VR2Gather or another upstream package and we work around it here, say so and offer to draft an issue for the upstream repository. I draft it, and the user posts it.
- **Prefer Inspector wiring.** When writing Unity C# code, if a connection (UnityEvent listener, field assignment, button onClick, etc.) could be wired in the Inspector or by a setup script instead of in `Start()`/`Awake()`, say what needs wiring and where, and ask the user to do it, rather than wiring it in code. The exception is wiring that genuinely can't be expressed in the Inspector (lambdas, connections that depend on runtime state).
